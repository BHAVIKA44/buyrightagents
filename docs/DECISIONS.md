# Engineering decisions

## Go and the standard library

Use Go for the core implementation and CLI. The deterministic evaluator uses only the standard library; no external dependencies are needed.

## Keep each increment focused

The current scope is the CLI, structured verification input, deterministic evidence evaluation, local decision policy, and cart snapshot binding. Do not pre-create packages or integrations for unimplemented systems.

## Separate interpretation from approval

The LLM-backed intent interpreter runs before a cart exists. It emits typed requirements, clarification questions, and unsupported constraints only. It has no evidence, cart snapshot, checkout, or decision fields. The deterministic evaluator accepts structured requirements and evidence, applies explicit operators, and returns `PASS`, `FAIL`, or `UNKNOWN` with evidence provenance.

## Use explicit values and policy

Typed values use explicit JSON type tags. Invalid or incomparable evidence is rejected instead of being coerced. Hard failures result in `BLOCK`; unresolved hard requirements result in `REVIEW`; `ALLOW` requires at least one hard requirement and all hard requirements passing. Preferences do not change the overall decision.

Use separate strict and inclusive operators where natural language distinguishes them: `less_than` versus `less_than_or_equal`, `greater_than` versus `greater_than_or_equal`, and `before` versus `before_or_equal` (similarly `after`). Monetary comparisons remain exact; `total_price_paise` is an integer number of paise and stays cart-scoped.

## Ground interpretation in explicit context

The caller supplies an RFC3339 reference timestamp, including its offset. The interpreter passes its local date and offset to the model and checks common relative dates with deterministic calendar arithmetic. It never reads the machine clock for interpretation. Model JSON is treated as untrusted, strict-decoded data; unknown and duplicate keys are rejected. Requirement IDs are generated by the application from normalized requirement content, not accepted from the model.

The model's source phrases must be found in the original request after lowercasing and collapsing punctuation/whitespace. This checks provenance of extracted phrases, but it cannot prove semantic completeness. Clarifications and unsupported constraints are surfaced rather than silently coerced into supported fields.

The standard-library HTTP client reads `BUYRIGHTAGENTS_LLM_API_KEY` and `BUYRIGHTAGENTS_LLM_MODEL`; `BUYRIGHTAGENTS_LLM_BASE_URL` optionally selects an OpenAI-compatible endpoint. Requests have a fixed timeout and bounded response body. There are no automatic retries. API credentials are never included in logs or committed configuration.

## Bind each report to a canonical snapshot

Hash a fixed struct representation of the full INR snapshot with item rows sorted by `item_id`. The report includes the SHA-256 digest. Snapshot changes require revalidation. The in-process mock gate also binds the complete verification context; any future persistent or external checkout gate must independently revalidate the live cart.

## Scope evidence to the cart or item

Requirements and evidence use explicit cart or item scope and subject IDs. Item evidence must match the cart item's product and variant. Cart total and promised delivery are derived from the snapshot, not caller evidence.

The built-in `total_price_paise` requirement is cart-scoped with numeric expected values and numeric/equality operators, including strict and inclusive bounds. The built-in `delivery_date` requirement is cart-scoped with validated ISO date values and date/equality operators, including strict and inclusive bounds. Empty snapshots are rejected so a purchase report cannot return `ALLOW` for an empty cart.

## Require mock evidence attestations at checkout

The ordinary local verifier retains a legacy diagnostic mode for existing structured fixtures. The mock checkout gate is stricter: it injects its clock into a trusted-evidence policy and accepts product evidence only when a configured in-process mock provider HMAC-attested the exact evidence fields and canonical cart hash. Missing, unknown, invalid, stale, future-dated, or replayed evidence is excluded, producing `UNKNOWN` rather than a product `FAIL`. A trusted negative claim may still establish `FAIL`.

The default checkout freshness window is 24 hours with a five-minute future tolerance. These are configurable when constructing the gate and are deterministic under an injected clock. The provider is a prototype trust boundary, not a real merchant identity, certificate system, or proof of claim truthfulness.

## Bind multi-item requirements explicitly

Single-item carts retain automatic product-level binding. Multi-item carts require explicit cart-context `item_bindings` from a unique product attribute to a concrete item ID. This lets evidence matching remain item/product/variant specific and avoids asking an LLM to choose cart items. Repeated attributes, unknown targets, and unqualified product requirements are ambiguous and produce `REVIEW`; cart-wide price and delivery constraints never use item bindings.

## Keep local evaluation separate from checkout

`ALLOW` reports only the result of this local evaluation. A snapshot hash binds the report to the caller-supplied data, but does not prove the live merchant cart matches it or authenticate seller claims. The current verifier does not execute checkout or payments.

## Prototype scope

BuyRightAgents is an independent prototype exploring a proposed capability. Documentation must not imply that Razorpay currently offers this exact feature or that no other company is pursuing it.
